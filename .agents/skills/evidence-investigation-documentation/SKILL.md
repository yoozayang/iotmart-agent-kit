# Evidence investigation

- Identify target, question, audience, sources, and output. Investigation is read-only; documentation writes need explicit authorization and applicable repository rules.
- Inspect actual source/config/runtime/log/API/JCR/UI before assigning responsibility or behavior. Do not infer platform structure from names or impose a standard layout.
- Cite paths, identifiers, URLs, commands, or observed state. Separate verified facts, labelled inferences, and unknowns.
- For maintenance findings capture: responsibility/behavior, actual location, confirmed purpose, maintenance impact, evidence.
- A How-to needs a goal, change location, change, and verification; a directory alone is not a How-to.
- Unless the user narrows the output, report: useful repo/system map; maintenance map; How-to candidates (ready / needs investigation / needs runtime verification); supported manual coverage; unknowns.
- Handoff completed scope, evidence limits, and executed vs remaining verification. Keep production, credential, and environment authorization boundaries.

Only when writing documentation, read [references/documentation.md](references/documentation.md). Before any Notion write or existing-document edit, read [references/content-preservation.md](references/content-preservation.md). Reading/investigation alone loads neither reference.
